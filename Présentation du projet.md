# Présentation du projet

Le projet est un jeu vidéo destiné principalement à **Steam**, développé avec **Unity 6.5 (6000.5.10f1) en C#**.

Il s’agit d’un **FPS rétro futuriste sombre, violent et grimdark**, inspiré dans son feeling général des FPS des années 1990 tels que *Doom*, *Heretic*, *Hexen* ou *Blood*, mais combiné avec des mécaniques de progression issues des hack’n’slash / ARPG tels que *Diablo II* ou *Titan Quest*.

Le jeu devra être jouable :

- en solo ;
- en coopération multijoueur ;
- jusqu’à environ **5 joueurs maximum** ;
- avec un système de lobby / invitation Steam.

Le développement doit rester adapté à un projet indépendant et éviter un scope excessif.

La priorité est de construire un gameplay solide, nerveux, modulaire et extensible avant d’augmenter fortement la quantité de contenu.

---

# Concept général

La boucle principale doit mélanger le plaisir immédiat d’un FPS rétro avec la progression à long terme d’un hack’n’slash.

Boucle de gameplay visée :

**Explorer → combattre → tuer → récupérer du loot → améliorer son équipement/build → progresser → affronter des zones et ennemis plus difficiles.**

Le joueur contrôle directement son personnage à la première personne dans des environnements 3D.

Les combats doivent être :

- rapides ;
- nerveux ;
- lisibles ;
- basés sur le déplacement ;
- basés sur l’esquive de projectiles ;
- capables d’afficher plusieurs ennemis simultanément ;
- orientés vers un sentiment de puissance ;
- proches dans leur philosophie des FPS des années 1990.

Le jeu ne cherche cependant pas à reproduire techniquement les limitations des anciens moteurs comme celui de Doom.

Les environnements seront de véritables environnements 3D modernes permettant notamment :

- plusieurs niveaux verticaux ;
- passerelles ;
- escaliers ;
- ennemis volants ;
- projectiles complexes ;
- éléments interactifs ;
- éclairage dynamique ;
- effets visuels modernes utilisés avec modération.

Le rendu devra cependant volontairement conserver une esthétique rétro.

# Science-fiction et composante démoniaque

L’univers ne sera pas limité à une science-fiction réaliste ou strictement technologique.

Il pourra intégrer une forte composante :

**démoniaque / occulte / extradimensionnelle.**

Le terme de « démon » pourra être utilisé directement dans l’univers.

Ces créatures pourront néanmoins être interprétées comme :

- des entités extradimensionnelles ;
- des formes de vie issues d’un autre plan ;
- des organismes liés à une énergie inconnue ;
- des créatures invoquées accidentellement ;
- des êtres libérés par des expériences scientifiques ;
- des parasites capables de posséder ou modifier des organismes ;
- des entités capables de fusionner avec des machines ;
- des intelligences capables de déformer la matière ou la réalité.

Il n’est pas nécessaire d’expliquer complètement leur origine.

Une part de mystère doit pouvoir subsister.

Les humains peuvent simplement les appeler « démons » parce qu’ils sont incapables de comprendre leur véritable nature.

Cette composante doit rester cohérente avec l’univers de science-fiction grimdark.

Elle ne doit pas transformer le jeu en fantasy médiévale.

Certaines zones pourront montrer une réalité altérée :

- architectures impossibles ;
- machines fusionnées avec de la chair ;
- murs organiques ;
- anomalies gravitationnelles ;
- distorsions visuelles ;
- phénomènes énergétiques ;
- mutations rapides ;
- portails ;
- dimensions parallèles.

Le rendu pourra utiliser :

- géométrie relativement simple ;
- décors low-poly ;
- sprites billboard ;
- modèles 3D low-poly lorsque nécessaire ;

# Personnage visible à la première personne

Le joueur ne devra pas être uniquement représenté par une caméra flottante et une arme.

Le **corps réel du personnage doit exister dans le monde**.

En regardant vers le bas, le joueur doit notamment pouvoir voir :

- son torse ;
- ses jambes ;
- ses pieds ;
- potentiellement certaines parties de ses bras selon les animations.

Le personnage devra donc posséder une représentation physique cohérente à la première personne.

Cette représentation devra également être compatible avec le multijoueur : les autres joueurs doivent voir le personnage complet dans le monde.

L’objectif est d’éviter autant que possible une séparation complète entre :

- un modèle uniquement utilisé en première personne ;
- un personnage totalement différent utilisé par les autres joueurs.

Des solutions techniques spécifiques pourront toutefois être utilisées lorsque nécessaire pour les animations FPS, à condition de maintenir une cohérence visuelle entre les deux représentations.

# Classes

Le jeu comportera des **classes de personnage**.

Les classes restent à définir précisément.

Une classe donnera notamment au personnage :

- une identité de départ ;
- une apparence de base ;
- des statistiques initiales ;
- potentiellement certaines spécialisations ou capacités ;
- éventuellement des avantages ou orientations particulières.

Cependant, les classes ne doivent pas complètement verrouiller les possibilités d’équipement ou de build.

Une classe représente surtout :

**le point de départ du personnage, pas nécessairement sa destination finale.**

Deux personnages de la même classe pourront donc évoluer de manière très différente selon leurs statistiques, leur équipement, leurs compétences et leurs choix de progression.

# Équipement et prérequis

Les équipements **ne seront pas limités par classe**.

Un objet ne devra donc pas imposer par défaut une condition telle que :

**« réservé à la classe Soldat ».**

Les équipements devront plutôt utiliser des **prérequis de statistiques**.

Exemple :

**Canon lourd**
- Force : 40
- Constitution : 25

**Fusil expérimental**
- Dextérité : 30
- Technologie : 45

**Artefact extradimensionnel**
- Volonté : 50

Cela doit permettre des builds hybrides et laisser davantage de liberté au joueur.

Un personnage pourra donc utiliser un équipement inhabituel pour sa classe initiale à condition d’avoir développé les statistiques nécessaires.

# Apparence et équipement

L’équipement porté devra modifier visuellement le personnage.

Cela concerne notamment :

- armure ;
- casque ;
- épaulières ;
- gants ;
- bottes ;
- protections ;
- implants visibles ;
- accessoires ;
- éventuellement certains éléments cybernétiques.

Le personnage possède donc :

**une apparence de base définie notamment par sa classe + une apparence dynamique modifiée par son équipement.**

Cette modification doit être visible :

- par le joueur lui-même ;
- sur son corps visible à la première personne ;
- par les autres joueurs en multijoueur.

Le système de personnages et d’équipement devra donc être pensé dès le départ pour supporter des éléments visuels interchangeables.

# Armes de corps à corps

Le joueur devra pouvoir combattre au corps à corps avec des **armes spécifiquement conçues pour la mêlée**.

Il ne s’agira pas uniquement d’un coup de secours commun à toutes les armes à distance.

Les armes de corps à corps devront constituer une véritable famille d’équipement pouvant notamment inclure :

- couteaux et lames industrielles ;
- épées ou haches technologiques ;
- masses, marteaux et outils lourds détournés ;
- tronçonneuses et armes mécaniques ;
- armes énergétiques ;
- armes biologiques ;
- artefacts démoniaques ou extradimensionnels.

Chaque arme pourra définir ses propres caractéristiques :

- portée ;
- vitesse d’attaque ;
- arc ou zone touchée ;
- puissance d’impact ;
- dégâts ;
- type de dégâts ;
- capacité à toucher plusieurs ennemis ;
- réactions et effets gore ;
- prérequis de statistiques ;
- affixes et effets spéciaux.

Les armes de mêlée devront pouvoir être obtenues comme du loot, équipées visuellement et intégrées aux mêmes systèmes de statistiques, raretés, affixes, compétences et synergies que les armes à distance.

Un personnage devra pouvoir construire un véritable **build orienté corps à corps**, quelle que soit sa classe de départ s’il remplit les prérequis nécessaires.

Les attaques devront rester rapides, lisibles et compatibles avec le déplacement nerveux du FPS.

Leur représentation devra être cohérente avec le corps visible à la première personne ainsi qu’avec ce que voient les autres joueurs en multijoueur.

Le système devra être data-driven afin d’ajouter de nouvelles armes de mêlée sans réécrire la logique centrale du combat.

# Histoire et narration

Le jeu comportera une **histoire principale**, volontairement relativement simple et facile à suivre.

La philosophie narrative devra se rapprocher davantage de jeux tels que *Diablo II* ou *Path of Exile* que d’un RPG extrêmement narratif.

L’histoire doit principalement servir à :

- donner un contexte aux actions du joueur ;
- justifier le déplacement entre différentes zones ;
- introduire progressivement l’univers ;
- présenter les factions ;
- expliquer ou suggérer l’origine des différentes menaces ;
- introduire les démons et phénomènes extradimensionnels ;
- donner des objectifs à court et moyen terme ;
- accompagner la montée en puissance du personnage ;
- conduire progressivement vers les principaux boss.

Le scénario ne doit pas prendre le dessus sur le gameplay.

La priorité reste :

**combat → exploration → progression → loot → développement du personnage.**

Il faudra donc éviter autant que possible :

- les cinématiques excessivement longues ;
- les dialogues obligatoires interminables ;
- les séquences retirant régulièrement le contrôle au joueur ;
- une exposition narrative trop importante ;
- les systèmes narratifs disproportionnés par rapport au reste du projet.

Un joueur principalement intéressé par le gameplay doit pouvoir avancer rapidement.

Un joueur intéressé par l’univers devra en revanche pouvoir découvrir beaucoup plus d’informations de manière facultative.

---

# Structure de l’histoire

L’histoire pourra être organisée en plusieurs :

- actes ;
- chapitres ;
- grandes zones narratives.

Une structure particulièrement adaptée serait :

**Acte → plusieurs zones → quêtes → découvertes → mini-boss → boss majeur → acte suivant.**

Chaque acte pourra notamment introduire :

- un environnement principal ;
- plusieurs zones secondaires ;
- de nouveaux types d’ennemis ;
- une ou plusieurs factions ;
- de nouvelles technologies ;
- de nouveaux phénomènes ;
- quelques quêtes ;
- plusieurs mini-boss ;
- un boss principal ;
- une évolution de la menace.

L’histoire pourra commencer de manière relativement simple.

Par exemple, le joueur pourrait initialement être confronté à :

- une installation ayant cessé de répondre ;
- une attaque ;
- une contamination ;
- un sabotage ;
- une rébellion ;
- une expérience scientifique hors de contrôle.

La véritable ampleur de la menace démoniaque ou extradimensionnelle pourra être révélée progressivement.

Le scénario exact reste à définir.

# Quêtes

Le jeu comportera des **quêtes relativement courtes et simples**.

Il pourra exister :

- des quêtes principales ;
- des quêtes secondaires ;
- des objectifs optionnels ;
- éventuellement certains événements ou objectifs contextuels.

Les quêtes doivent être compatibles avec le rythme rapide du FPS/ARPG.

Exemples d’objectifs :

- atteindre une zone ;
- trouver un personnage ;
- éliminer une cible ;
- tuer un boss ;
- récupérer un objet ;
- activer un système ;
- réparer une installation ;
- désactiver une installation ;
- défendre une position ;
- détruire plusieurs objectifs ;
- nettoyer une zone ;
- retrouver plusieurs éléments ;
- ouvrir un accès ;
- enquêter sur une contamination ;
- fermer un portail ;
- détruire une anomalie extradimensionnelle.

Il faut éviter autant que possible les objectifs artificiellement répétitifs.

Par exemple :

**« tuer 25 ennemis identiques uniquement parce qu’une quête demande d’en tuer 25 »**

ne doit pas constituer le cœur du système de quêtes.

Si ce type d’objectif existe, il doit idéalement se réaliser naturellement pendant l’exploration ou le combat.

---

# Quêtes secondaires

Les quêtes secondaires pourront notamment servir à :

- développer l’univers ;
- présenter des personnages secondaires ;
- raconter l’histoire d’une zone ;
- approfondir certaines factions ;
- découvrir des expériences passées ;
- révéler des informations facultatives ;
- débloquer des zones secrètes ;
- obtenir du matériel particulier ;
- obtenir des récompenses rares ;
- affronter des ennemis optionnels ;
- affronter des boss optionnels.

Les quêtes secondaires doivent rester relativement courtes.

Le but n’est pas de créer des centaines de quêtes complexes comportant de multiples branches narratives.

Il vaut mieux proposer :

**moins de quêtes, mais avec un contexte, un lieu, un combat ou une récompense intéressante.**

---

# Récompenses de quête

Les quêtes pourront fournir :

- expérience ;
- monnaie ;
- équipement ;
- objets rares ;
- objets uniques ;
- points de statistiques ;
- points de compétences ;
- accès à de nouvelles zones ;
- nouveaux services ;
- nouveaux vendeurs ;
- nouvelles fonctionnalités.

Certaines quêtes pourront proposer un choix entre plusieurs récompenses.

Exemple :

**Récompense au choix :**

- implant orienté armes lourdes ;
- module orienté bouclier ;
- artefact orienté effets extradimensionnels.

Ces choix pourront renforcer les possibilités de build.

# Philosophie narrative

La règle générale concernant la narration sera :

**Le gameplay doit raconter l’aventure autant que les dialogues.**

Le joueur doit pouvoir comprendre une grande partie de ce qui se passe simplement en :

- explorant ;
- observant les environnements ;
- combattant ;
- rencontrant de nouveaux ennemis ;
- découvrant de nouvelles technologies ;
- trouvant des objets ;
- rencontrant les conséquences des événements ;
- avançant vers des zones de plus en plus altérées.

L’histoire doit donner du sens au voyage sans ralentir inutilement le FPS.

# Système de progression

La partie hack’n’slash doit être centrale.

La progression ne doit pas se limiter à augmenter des statistiques.

Les équipements doivent pouvoir modifier réellement la manière de jouer.

Exemple :

Un fusil peut :

- traverser plusieurs ennemis ;
- faire exploser les ennemis surchauffés ;
- restaurer le bouclier lors d’une explosion ;
- augmenter temporairement sa cadence après une élimination.

Un autre équipement peut créer une synergie avec ces effets.

Le joueur doit progressivement pouvoir construire un véritable **build**.

Les systèmes de progression pourront inclure :

- statistiques ;
- niveaux ;
- armes ;
- armures ;
- implants ;
- modules ;
- compétences ;
- capacités actives ;
- capacités passives ;
- affixes ;
- effets spéciaux ;
- synergies ;
- technologies extraterrestres ;
- artefacts extradimensionnels ;
- équipements corrompus.

Il faut privilégier les effets transformant le gameplay plutôt que les simples bonus numériques.

---

# Compétences actives et passives

Le jeu devra comporter des **compétences actives** et des **compétences passives** constituant une partie importante de la progression ARPG et de la création des builds.

## Compétences actives

Les compétences actives devront être équipées par le joueur puis déclenchées directement pendant le combat à l’aide de commandes dédiées et reconfigurables.

Elles pourront notamment inclure :

- attaques spéciales ;
- compétences liées aux armes à distance ou de mêlée ;
- ruées, bonds ou téléportations courtes ;
- grenades et explosifs ;
- drones ;
- boucliers temporaires ;
- capacités de contrôle ;
- hacking ;
- effets électriques, plasma ou énergétiques ;
- pouvoirs biologiques ;
- capacités démoniaques ou extradimensionnelles.

Selon la compétence, son utilisation pourra être limitée par :

- un temps de recharge ;
- une ou plusieurs charges ;
- une ressource ;
- une condition de déclenchement ;
- une durée d’activation ;
- ou une combinaison de ces éléments.

Les compétences actives devront rester rapides, réactives et compatibles avec le rythme d’un FPS nerveux.

Elles ne devront pas imposer régulièrement de longues animations retirant inutilement le contrôle au joueur.

## Compétences passives

Les compétences passives devront modifier durablement ou conditionnellement le fonctionnement du personnage et de son build sans nécessiter une activation directe.

Elles pourront notamment :

- modifier le comportement d’une arme ;
- renforcer ou transformer un type de dégâts ;
- ajouter des effets après une élimination ou un coup critique ;
- modifier la mobilité ;
- renforcer le bouclier, la vie ou les résistances ;
- interagir avec la surchauffe, les explosions ou les effets de statut ;
- améliorer les armes de mêlée ;
- modifier les drones ou les capacités technologiques ;
- créer des effets liés à la corruption ou aux phénomènes extradimensionnels ;
- déclencher des synergies avec l’équipement, les affixes ou d’autres compétences.

Les passifs transformant réellement le gameplay devront être privilégiés par rapport aux simples augmentations numériques lorsque cela est pertinent.

## Progression et builds

Le mode précis d’acquisition et d’amélioration des compétences reste à définir, mais le système devra pouvoir prendre en charge :

- des points de compétences ;
- des prérequis ;
- plusieurs niveaux ou améliorations ;
- des choix exclusifs lorsque cela apporte un intérêt réel ;
- des compétences liées à une classe, une technologie, un équipement ou une découverte ;
- des interactions entre compétences actives et passives.

Les classes pourront orienter les premières compétences disponibles sans obliger tous les personnages d’une même classe à suivre le même build.

Le système devra être data-driven afin de pouvoir ajouter ou modifier une compétence sans réécrire les systèmes centraux de combat et de progression.

Les mêmes définitions de compétences devront être utilisées en solo et en multijoueur, tandis que leur déblocage et leur progression suivront les règles de persistance propres à chaque mode.

En multijoueur, les activations, ressources, temps de recharge et effets importants pour le gameplay devront être correctement validés et synchronisés.

# Builds

Le build d’un personnage sera déterminé par une combinaison de :

**classe + statistiques + compétences + équipement + affixes + effets spéciaux.**

Les classes servent de point de départ mais ne doivent pas enfermer le joueur dans un build unique.

Exemples de directions possibles :

- plasma / surchauffe ;
- explosions ;
- shotgun / armes de mêlée / combat rapproché ;
- armes lourdes ;
- mobilité ;
- drones ;
- hacking ;
- contrôle ;
- bouclier ;
- dégâts électriques ;
- armes extraterrestres ;
- technologie démoniaque ;
- corruption ;
- effets extradimensionnels.

L’objectif est de favoriser :

- expérimentation ;
- hybridation ;
- synergies ;
- theorycrafting.

---

# Loot

Le loot doit être un moteur majeur de progression et de rejouabilité.

Les objets pourront posséder :

- niveaux ;
- raretés ;
- statistiques ;
- préfixes ;
- suffixes ;
- effets spéciaux ;
- capacités uniques ;
- prérequis de statistiques.

Certains objets pourront provenir :

- de technologies humaines ;
- de technologies extraterrestres ;
- d’organismes biologiques ;
- d’entités démoniaques ;
- de phénomènes extradimensionnels.

Le système doit être **data-driven et modulaire**.

Ajouter :

- un objet ;
- un affixe ;
- un effet ;
- une nouvelle rareté ;
- une nouvelle synergie ;

doit nécessiter aussi peu que possible de modifications du code central.

# Modes de jeu et séparation des personnages

Le jeu proposera deux environnements de progression distincts :

- **Solo**
- **Multijoueur**

Les personnages créés dans ces deux modes sont **strictement séparés**.

Un personnage créé en mode solo ne pourra jamais être utilisé en multijoueur.

Inversement, un personnage créé pour le multijoueur sera destiné uniquement au multijoueur.

Il ne devra donc pas exister de système permettant :

- d’importer un personnage solo vers le multijoueur ;
- d’exporter un personnage multijoueur vers le solo ;
- de copier l’inventaire d’un mode vers l’autre ;
- de transférer des objets ;
- de transférer de l’expérience ;
- de transférer des statistiques ;
- de transférer de la monnaie ;
- de transférer des quêtes ;
- de transférer de la progression narrative ;
- de transférer toute autre progression entre les deux environnements.

Cette séparation est volontaire et constitue un principe fondamental du projet.

---

# Personnages solo

Les personnages solo évoluent exclusivement dans l’environnement solo.

Leur progression comprend notamment :

- niveau ;
- expérience ;
- statistiques ;
- compétences ;
- inventaire ;
- équipement ;
- monnaie ;
- progression ;
- loot ;
- quêtes ;
- progression narrative.

La sauvegarde solo pourra être stockée localement sur la machine du joueur.

La protection contre la modification des sauvegardes solo n’est pas une priorité majeure, puisque ces données ne pourront jamais être utilisées dans l’environnement multijoueur.

Le personnage solo reste cependant soumis aux mêmes systèmes fondamentaux de gameplay que les personnages multijoueur.

Le solo et le multijoueur doivent partager autant que possible les mêmes systèmes de gameplay.

C’est principalement leur système de persistance et de sécurité qui diffère.

---

# Personnages multijoueur

Lorsqu’un joueur crée un personnage destiné au multijoueur, celui-ci devient un **personnage multijoueur persistant**.

Ce personnage ne pourra être utilisé que dans les parties multijoueur.

Les personnages multijoueur devront être **sauvegardés sur des serveurs contrôlés par le jeu**.

Le but principal est d’éviter qu’un joueur puisse simplement modifier un fichier local pour altérer son personnage.

Le client ne devra pas être considéré comme une source de confiance concernant notamment :

- niveau ;
- expérience ;
- statistiques ;
- inventaire ;
- équipement ;
- monnaie ;
- progression ;
- objets obtenus ;
- propriétés des objets ;
- compétences débloquées ;
- quêtes terminées ;
- progression narrative permanente.

Les données persistantes importantes devront donc être stockées et, lorsque cela est pertinent, validées côté serveur.

Le personnage multijoueur devra être associé au compte ou à l’identifiant du joueur.

---

# Séparation Solo / Multijoueur

La séparation peut être représentée ainsi :

**SOLO**

Création personnage solo  
↓  
Sauvegarde locale  
↓  
Progression solo  
↓  
Loot / quêtes / histoire solo  
↓  
Personnage utilisable uniquement en solo

**MULTIJOUEUR**

Création personnage multijoueur  
↓  
Association au compte joueur  
↓  
Sauvegarde serveur  
↓  
Progression multijoueur  
↓  
Loot / quêtes / histoire multijoueur  
↓  
Personnage utilisable uniquement en multijoueur

Il ne doit exister **aucune passerelle de progression entre ces deux branches**.

---

# Quêtes et multijoueur

Le système de quêtes devra fonctionner correctement en coopération.

Chaque type de progression devra permettre de définir clairement si un objectif est :

- individuel ;
- partagé par le groupe ;
- validé pour tous les participants ;
- lié au personnage ;
- lié temporairement à la session.

Dans la mesure du possible, les quêtes coopératives doivent éviter les situations où tous les joueurs doivent répéter individuellement exactement la même interaction.

Par exemple :

si cinq joueurs possèdent une quête demandant de tuer un boss et qu’ils participent ensemble au combat, tous les personnages éligibles devraient normalement pouvoir obtenir la validation.

La progression permanente des quêtes d’un personnage multijoueur devra être sauvegardée côté serveur.

La progression des quêtes d’un personnage solo restera associée à sa sauvegarde locale.

---

# Multijoueur

Le multijoueur vise des groupes allant jusqu’à environ **5 joueurs**.

Les sessions de jeu pourront utiliser un modèle :

**Host / Client**

Un joueur pourra donc héberger la simulation de la partie pour le groupe.

Steam pourra notamment être utilisé pour :

- lobby ;
- invitations ;
- connexion entre joueurs ;
- identification ;
- éventuellement matchmaking léger.

Il faut cependant distinguer clairement :

**l’hébergement de la session de jeu**

et

**l’autorité sur la progression permanente des personnages.**

Même si un joueur héberge la partie, cela ne signifie pas que cet hôte possède l’autorité absolue sur les personnages.

La progression persistante multijoueur doit rester contrôlée par l’infrastructure serveur du jeu.

---

# Sécurité et anti-triche

La règle générale est :

**Le solo peut utiliser des données locales.  
Le multijoueur ne doit pas faire confiance aux données locales.**

Il est impossible d’empêcher totalement la triche dans un jeu client.

L’objectif est donc principalement de protéger les éléments persistants importants.

Les données multijoueur sensibles devront être validées côté serveur autant que possible.

Il faudra éviter de faire confiance aveuglément à des informations telles que :

- quantité de monnaie ;
- création d’objet ;
- niveau ;
- expérience ;
- statistiques ;
- propriétés d’un objet ;
- progression permanente ;
- quêtes terminées ;
- récompenses obtenues.

Les décisions de sécurité devront cependant rester proportionnées au projet afin de ne pas transformer le développement en création d’une infrastructure MMO disproportionnée.

---

# Principe architectural Solo / Multijoueur

Les systèmes de gameplay doivent autant que possible être communs entre solo et multijoueur.

Par exemple :

- CharacterStats ;
- Inventory ;
- Equipment ;
- Skills ;
- Items ;
- Loot ;
- CharacterClass ;
- Damage ;
- Status Effects ;
- Progression ;
- Quests ;
- Quest Objectives ;

ne doivent pas être réécrits séparément pour chaque mode.

En revanche, la persistance doit être différente.

Conceptuellement :

**Gameplay commun**

↓

**SoloPersistence**
- sauvegarde locale ;
- personnage solo ;
- progression narrative locale.

ou

**MultiplayerPersistence**
- sauvegarde serveur ;
- personnage multijoueur ;
- validation des données importantes ;
- progression narrative serveur ;
- association au compte du joueur.

Cette séparation devra être prise en compte dès la conception de l’architecture.

# Clavier, manette et reconfiguration des commandes

Le jeu devra détecter la **disposition de clavier utilisée par le joueur**, notamment les configurations :

- **AZERTY** ;
- **QWERTY** ;
- et, autant que possible, les autres dispositions courantes prises en charge par le système.

Les commandes proposées par défaut devront être adaptées à la disposition détectée.

Par exemple :

- un clavier QWERTY pourra utiliser **WASD** pour le déplacement ;
- un clavier AZERTY pourra utiliser **ZQSD** pour le déplacement.

La détection automatique devra servir à choisir un profil initial cohérent ou à restaurer les commandes par défaut.

Elle ne devra jamais écraser des touches déjà personnalisées par le joueur.

Le joueur devra pouvoir **modifier les touches du clavier ainsi que les commandes de la manette** depuis un menu dédié.

Les profils clavier/souris et manette devront pouvoir être configurés séparément.

Le joueur devra également pouvoir régler la **sensibilité de la souris** depuis ce menu.

Ce réglage devra :

- proposer une plage suffisamment large pour convenir aux sensibilités basses comme élevées ;
- être appliqué immédiatement afin que le joueur puisse tester facilement le résultat ;
- être sauvegardé localement ;
- être conservé entre les sessions de jeu ;
- rester indépendant du personnage solo ou multijoueur utilisé.

Le système de reconfiguration devra notamment permettre :

- de sélectionner une action ;
- d’attribuer une nouvelle touche, un nouveau bouton ou une nouvelle commande de manette ;
- d’identifier clairement la touche ou la commande actuellement utilisée ;
- de détecter les conflits entre plusieurs actions ;
- de confirmer, remplacer ou annuler une attribution conflictuelle ;
- de restaurer séparément les commandes clavier/souris ou manette par défaut ;
- de sauvegarder les commandes personnalisées ;
- de conserver ces commandes entre les sessions de jeu.

Les noms de touches affichés dans l’interface devront correspondre autant que possible à la disposition réellement utilisée par le joueur.

Lorsque cela est possible, les indications de boutons devront également correspondre au type de manette détecté.

L’interface devra pouvoir afficher automatiquement les indications correspondant au dernier périphérique utilisé, sans empêcher le joueur d’alterner librement entre clavier/souris et manette.

Les commandes ne devront pas être écrites directement en dur dans les scripts de gameplay.

Les préférences de contrôle constituent des réglages locaux du joueur et ne doivent pas dépendre d’un personnage solo ou multijoueur.

- l’interface reste nette ;

- le jeu reste utilisable correctement jusqu’en 4K.

# Philosophie concernant le scope

Le projet ne doit pas commencer comme un immense ARPG.

Le développement doit d’abord valider la boucle fondamentale :

**déplacement → combat → kill → feedback violent → loot → équipement → progression → quête → augmentation de puissance → nouveau combat.**

Une première version jouable peut volontairement comporter :

- une classe ;
- quelques statistiques ;
- quelques armes ;
- quelques équipements visibles ;
- quelques compétences ;
- quelques familles de loot ;
- une dizaine d’ennemis ;
- un premier démon ;
- un environnement principal ;
- quelques zones ;
- un ou deux boss ;
- une quête principale simple ;
- une quête secondaire simple ;
- quelques éléments narratifs.

Une fois cette boucle réellement amusante, les systèmes pourront être enrichis progressivement.

Le multijoueur complexe, le crafting avancé, de nombreuses classes, des centaines d’objets ou une histoire excessivement ambitieuse ne doivent pas empêcher la création rapide d’un prototype fonctionnel.
